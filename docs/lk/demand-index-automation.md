# ТЗ: ежемесячный «Индекс спроса» из кабинета

Для команды ЛК. Сейчас индекс на navilet.ru/indeks-sprosa считается вручную
скриптом `scripts/demand-index.sql` (репозиторий сайта) и переносится в
`src/lib/seo/demand-index.ts`. Нужно, чтобы кабинет считал выпуск сам раз в
месяц, владелец подтверждал его в Telegram, а сайт пересобирался с новыми
цифрами.

## Поток

1. **1-го числа, 06:00 МСК** — новая задача `_job_demand_index` в `scheduler.py`
   (рядом с `_job_monthly_reports`, `CronTrigger`).
2. Задача считает выпуск за период «1 июня (или 4 месяца назад) — последний
   день прошлого месяца», прогоняет проверки качества (ниже) и сохраняет
   снимок в новую таблицу `demand_index_snapshots` со статусом `draft`.
3. Бот (`telegram_bot.py`) шлёт владельцу черновик: главные цифры, изменения
   к прошлому выпуску, предупреждения проверок и служебные размеры выборок.
   Кнопки «Опубликовать» / «Отклонить».
4. «Опубликовать» → статус `published` → запрос на хук деплоя сайта (см. ниже).
5. Сайт в `prebuild` забирает `GET /api/public/demand-index/latest` и кладёт
   ответ в `src/lib/seo/demand-index.json`. Если эндпоинт недоступен — сборка
   берёт последний сохранённый файл, а не падает.

## Таблица

```sql
create table demand_index_snapshots (
  id bigserial primary key,
  edition varchar(7) not null unique,   -- '2026-09'
  period_from date not null,
  period_to date not null,
  status varchar(16) not null default 'draft',  -- draft | published | rejected
  payload jsonb not null,               -- то, что уходит на сайт
  internal jsonb not null,              -- размеры выборок, доля крупнейшего агентства
  warnings jsonb not null default '[]',
  created_at timestamptz not null default now(),
  published_at timestamptz,
  published_by varchar(64)
);
```

## Правила расчёта

Совпадают с `scripts/demand-index.sql` — его стоит перенести как есть:

- **Кто входит.** Новое поле `companies.exclude_from_index boolean default false`.
  Сразу `true` для «Навылет AI — Демо», «Магазин Путешествий (ТЕСТ — оплата)»,
  «MGP Legacy Archive» и любых тестовых компаний. Сейчас признака нет, тестовые
  видны только по названию — это главный риск «грамотных данных по всем
  тенантам».
- **Единица** — диалог; берётся последний поиск в диалоге (`tour_searches`).
- **Страны** — словарь `_COUNTRY_NAMES` из `dashboard_api.py`. ID без названия
  не отбрасывать молча: если их доля > 1% — предупреждение.
- **Публикуем**: доли стран, тренд в п.п. (последний месяц к предыдущим месяцам
  периода), медианы бюджета, ночей, дней до вылета, доли «с детьми», «всё
  включено» (по тексту сообщений туриста), «без перелёта», спрос по месяцу
  вылета, помесячные доли.
- **Не публикуем**: число диалогов и поисков (решение владельца), звёздность
  (её подставляет бот), города вылета и месячные объёмы (зависят от состава
  агентств), названия агентств.

## Проверки качества

Блокируют публикацию (черновик создаётся, но с пометкой «не публиковать»):

- диалогов с поиском за последний месяц меньше 200;
- у пяти крупнейших стран есть ID без названия;
- сумма долей не 100% ± 1.

Показываются как предупреждения, решает владелец:

- **Порог выборки.** Медиана по стране — только при n ≥ 40, иначе `null`
  (на сайте «мало данных»). Месяц вылета — только при n ≥ 100.
- **Параметры туриста, а не бота.** Каждый месяц пересчитывать долю
  диалогов, где бюджет, дети и ночи подтверждаются текстом сообщений (сейчас
  77–98%). Если у параметра доля упала ниже 70% — бот начал подставлять его сам,
  метрику не публиковать.
- **Скачки.** Доля страны изменилась больше чем на 10 п.п. — показать, какое
  агентство дало сдвиг (в `internal`, не на сайт).
- **Концентрация.** Доля крупнейшего агентства (сейчас ≈78% диалогов с
  поиском). Если выросла на 10+ п.п. или подключился новый крупный тенант —
  тренд считать только по агентствам, активным в обоих периодах (как «те же
  магазины» в ритейле), иначе рост доли будет артефактом подключения.

## Публичный эндпоинт

`GET /api/public/demand-index/latest` и `/api/public/demand-index/{edition}` —
только `published`, только `payload`. Без авторизации, кэш 1 час. Формат —
как `demandIndex` в `src/lib/seo/demand-index.ts` сайта (edition, published,
periodFrom/To, periodLabel, trendLabel, overall, countries, bySearchMonth,
byDepartureMonth). Поле `internal` наружу не отдаётся никогда.

## Хук деплоя сайта

На сервере сайта (5.129.241.199) — отдельный SSH-ключ с `command=` в
`authorized_keys`, который может только запустить `/root/navilet-deploy.sh`.
Кабинет вызывает его после «Опубликовать». Скрипт уже умеет: pull, сборка,
смоук-тесты, IndexNow.

## Сетевой барометр в кабинете

`collect_network_barometer` в `reports_service.py` считает иначе: по кликам
«Оформить тур» за 14 дней и без исключения демо. Агентства видят его в письмах
и в разделе «Прогнозы», а на сайте — индекс по поискам за месяц. Цифры будут
расходиться. Варианты: перевести барометр на ту же выборку (исключить
`exclude_from_index`) и явно подписать «по кликам за 14 дней», либо брать
долю стран для барометра из последнего опубликованного снимка.

## Что делает сайт (со стороны сайта, не ЛК)

- `prebuild`: скачать JSON, проверить схему, при ошибке — оставить прошлый файл.
- Архив выпусков `/indeks-sprosa/2026-09` и т. д., `/indeks-sprosa` — последний.
- Перевести сравнения в текстах `/spros/*` («максимум среди направлений»,
  «вдвое чаще», курорты) на условия от данных, чтобы текст не врал после
  обновления.

## Оценка

ЛК: таблица + поле компании + задача + бот + эндпоинт — 2–3 дня. Хук деплоя —
час. Сайт — 1 день.
